Prepare the Phase 6 ODE candidate dataset and the findings from Phase 7 for machine learning. This phase will define a shared baseline feature set and preprocessing pipeline that both Random Forest and XGBoost can use for a fair comparison in Phase 9.

## 2. Define the shared baseline feature set

Member 2 should define the baseline features that both models will initially use.

These are candidate features to verify against the actual Phase 6 schema, not assumptions that every column already exists.

| Feature group           | Example features                                                           | Why they matter                                       |
| ----------------------- | -------------------------------------------------------------------------- | ----------------------------------------------------- |
| Truck capacity          | Maximum payload weight, maximum volume                                     | Defines the truck's physical limits                   |
| Current utilization     | Current weight utilization, current volume utilization                     | Shows how much of the truck is already occupied       |
| Remaining capacity      | Remaining weight and remaining volume                                      | Indicates the space available for consolidation       |
| Proposed cargo          | Candidate cargo weight, candidate cargo volume, proposed quantities        | Measures the load being considered                    |
| Inventory               | Available inventory for proposed SKUs                                      | Determines whether the cargo can actually be supplied |
| Open demand             | Eligible open-order quantity for the destination                           | Indicates whether sufficient demand exists            |
| Demand patterns         | Historical SKU-destination demand, demand variability, recent demand trend | Captures recurring demand patterns                    |
| Product characteristics | SKU count, average unit weight, total product volume, product category     | Describes the proposed cargo                          |
| Route and destination   | Route, destination city, route compatibility                               | Captures logistical constraints and differences       |
| Planning time           | Hour, day of week, time-related features                                   | Captures temporal patterns known at prediction time   |

The target is `Became_FTL`. It is the label the models will learn to predict, not an input feature.

Do not include future dispatch status, final truck utilization, actual future shipped quantities or other information unavailable when the prediction is made.

## 3. Perform feature engineering

Transform existing operational columns into features that better represent the PTL-to-FTL problem.

### 3.1 Capacity and utilization features

Calculate, where not already available:

- Current weight utilization percentage.
- Current volume utilization percentage.
- Remaining weight capacity.
- Remaining volume capacity.
- Projected weight utilization after adding the proposed cargo.
- Projected volume utilization after adding the proposed cargo.

For example:

\\[ \text{Weight Utilization (\\%)} = \frac{\text{Current Load Weight}}{\text{Maximum Payload Weight}}\times100 \\]

\\[ \text{Projected Weight Utilization (\\%)} = \frac{\text{Current Load Weight}+\text{Candidate Cargo Weight}} {\text{Maximum Payload Weight}}\times100 \\]

Apply equivalent calculations for volume.

A candidate must respect both weight and volume limits. High utilization in one dimension does not guarantee that the cargo fits in the other.

### 3.2 Inventory and demand features

Where the underlying data supports them, engineer:

- Total available inventory for proposed SKUs.
- Total eligible open demand for the candidate destination.
- Demand-to-stock ratio.
- Inventory sufficiency relative to proposed quantities.
- Historical average demand for the relevant SKU and destination.
- Recent demand trend or demand variability.

Handle zero denominators explicitly when computing ratios. Ensure inventory and demand values are reconstructed as of the prediction timestamp, not taken from future snapshots.

### 3.3 Cargo and product features

Possible engineered features include:

- Total proposed cargo weight and volume.
- Number of distinct SKUs in the candidate.
- Weighted average unit weight.
- Cargo quantity relative to eligible open demand.
- Cargo quantity relative to available inventory.
- Product-category composition of the proposed combination.

Use definitions that are consistent across candidates. If a candidate contains multiple SKUs, document how each aggregate is calculated.

### 3.4 Route and time features

- Encode route and destination categories.
- Extract hour, day of week or other useful calendar features from the planning timestamp.
- Consider route-specific demand patterns if sufficient historical observations exist.

Avoid arbitrary numeric encoding of categories when the numbers would imply a false ordering.

Expected outcome: A documented baseline feature set with precise definitions, formulas and data sources.

## 4. Handle missing values and inconsistent data

Inspect missingness after feature engineering, because derived features can introduce new missing values.

Tasks:

1. Determine why values are missing rather than automatically replacing everything with zero.
2. Use `SimpleImputer` for suitable numeric and categorical features.
3. Use a consistent missing-value strategy for both models where practical.
4. Investigate invalid values, such as negative remaining capacity caused by incorrect upstream calculations.
5. Validate that ratios, percentages and engineered features fall within plausible ranges.
6. Do not use target labels to impute input features.

Remember: a genuine zero inventory level differs from an unknown inventory value. Preserve that distinction.

## 5. Build the preprocessing pipeline

Integrate the relevant data-preprocessing topics from your syllabus:

- `SimpleImputer`
- `StandardScaler`
- `OneHotEncoder`
- `ColumnTransformer`
- `Pipeline`

A possible baseline pipeline is:

```
from sklearn.compose import ColumnTransformerfrom sklearn.pipeline import Pipelinefrom sklearn.impute import SimpleImputerfrom sklearn.preprocessing import StandardScaler, OneHotEncoderfrom sklearn.ensemble import RandomForestClassifiernumeric_pipeline = Pipeline([    ("imputer", SimpleImputer(strategy="median")),    ("scaler", StandardScaler())])categorical_pipeline = Pipeline([    ("imputer", SimpleImputer(strategy="most_frequent")),    ("encoder", OneHotEncoder(handle_unknown="ignore"))])preprocessor = ColumnTransformer([    ("numeric", numeric_pipeline, numeric_features),    ("categorical", categorical_pipeline, categorical_features)])baseline_pipeline = Pipeline([    ("preprocessor", preprocessor),    ("model", RandomForestClassifier(random_state=42))])
```

This is an illustrative pipeline for Random Forest; it is not the final training script. The numeric and categorical column lists must be created from the actual dataset.

For XGBoost, the same baseline feature definitions should be used, but preprocessing may be adapted to its input requirements. Scaling is generally not necessary for tree-based models, so document whether it is retained or omitted for each algorithm.

Critical rule: Fit imputers, scalers and encoders using training data only. Do not fit preprocessing on the full dataset before splitting.

## 6. Create a leakage-safe training and test split

This is especially important because CargoSense contains timestamped planning runs and repeated operational snapshots.

Tasks:

1. Separate the target `Became_FTL` from the input features.
2. Use a chronological training/validation/test strategy where feasible.
3. Keep candidates from the same planning run, or other closely related operational groups, from leaking across splits where this is necessary to preserve realistic evaluation.
4. Make the split identical for both baseline models.
5. Inspect target class proportions in each split.
6. Record the date ranges and candidate counts for every split.

A random split may produce overly optimistic results if closely related candidates appear in both training and test sets.

If the dataset does not contain enough independent time periods or positive outcomes for a reliable split, document that limitation rather than presenting weak evaluation as conclusive.
